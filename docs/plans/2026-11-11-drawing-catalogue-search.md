# Drawing to Analysis — 치공구표준집 찾기 · 사진으로 가까운 도면 찾기 (계획)

작성 2026-11-11 · 상태: 0~2단계 구현(미커밋), 3단계는 사용자 결정 대기 1건(맨 아래)

## 배경

- 사용자는 검토할 부재가 사내 **'18 치공구표준집(FINAL)(2018.12.3)**(166쪽, 도면 155쪽)에 있는지 모른다.
  지금은 PDF 를 직접 올리고 **쪽 번호를 손으로** 넣어야 한다.
- 탐색 결과(2026-11-11, 스크립트·결과 = `%TEMP%/claude/explore_book/`):
  - 목차(PDF 3~6쪽)는 글자 층이 있어 **155종의 명칭·기호·쪽**이 그대로 나온다. 도면 쪽 = PDF 쪽 − 11.
  - PDF 7쪽에 러그 계열 용도표(D = 수직 LIFTING·T/O 보조, T = T/O 전용, A = T/O 곡부, L = LAPPING 취부, B = STIFF SIDE 취부).
  - 도면 쪽은 모두 같은 양식(머리말 품명·기호 / 도면 영역 / BOM / 표제란·중량·안전하중). 도면 글자는 선 글자라 글자 층이 없다.
  - 새 엔진으로 변환되는 쪽은 지금 **4쪽**(L-25·30·40·50). 나머지는 템플릿이 없다 → 찾기 화면은 '변환 가능 / 도면만' 을 구분해 보여야 한다.
  - 종이 도면 사진 → 쪽 찾기 실험(numpy 만): 도면 영역 비교로 보통 사진 top-1 95%·top-5 99%, 기울임·원근이 큰 사진 48%·63%.
- 사용자 방향(2026-11-11): **사진은 '사진에서 형태를 파악해 가장 가까운 도면을 찾는' 방식**으로 간다.

## 목표

1. 기호·명칭·용도·하중으로 도면집에서 부재를 찾고, 고르면 **그 쪽이 바로 변환**된다(파일 올리기·쪽 번호 입력 없음).
2. 사진(실물 또는 종이 도면)을 넣으면 **형태가 가장 가까운 도면 후보 5개**를 보여 주고 사용자가 고른다.
   자동 확정은 하지 않는다 — 같은 계열은 모양이 닮고 크기만 달라 마지막 선택은 사람(하중·기호 확인)이 한다.

## 단계

### 0단계 — 색인 만들기 (도면집 1회 처리)

- `scripts/drawing_book_index.py`(70 에서 실행, 결과만 커밋): 목차 → `book_index.json`
  - 항목 = `{code, aliases[], name, group, bookPage, pdfPage, family, swl_t?, usage?, analysable}`
  - `aliases`: 'D-2, D-2A, D-2P' → 세 기호 모두 검색되게. `swl_t`: 러그 기호의 숫자(D-25 → 25 t), 그 밖은 비움.
  - `family`·`usage`: 7쪽 용도표를 손으로 옮긴 표(러그 6계열).
  - `analysable`: 반목(콘크리트·목재·플라스틱)·샤클(구매품)은 false — 찾기는 되되 '해석 대상 아님' 표시.
  - `convertible`: 엔진 전수 시험(sweep) 결과로 채운다(지금 L-25·30·40·50). 템플릿이 늘면 다시 돌린다.

### 3단계 — 사진으로 가까운 도면 찾기 (형태 비교) ★실현성 확인 후 진행

방식: 사진에서 부재 **윤곽(실루엣)**을 뽑고, 도면집 각 쪽 **정면도 윤곽**과 형태를 비교해 가까운 순으로 5개.

- 도면 쪽 특징값(0단계에서 1회): 도면 영역의 벡터 선에서 가장 큰 닫힌 외곽 + 안쪽 원(핀 구멍)을 찾는다
  (lugshell `pdf_vectors` 가 이미 선·원호를 읽는다). 특징 = 크기·회전에 무관한 값들 —
  외곽의 푸리에 기술자, 가로세로비, 구멍 위치·지름 / 외곽 크기 비, 구멍 수.
- 사진 쪽: 사용자가 부재를 사각형으로 고름 → 배경과 분리(밝기·가장자리 기준) → 가장 큰 윤곽 + 안쪽 구멍 → 같은 특징.
  분리가 틀리면 사용자가 문턱값을 밀어 조정할 수 있게 윤곽을 겹쳐 보여 준다.
- 종이 도면 사진이면 0단계 실험의 '도면 영역 비교'(top-5 99%)가 더 정확하다 → 두 방식을 함께 돌려 후보를 합친다.
- 한계(미리 알림): 같은 계열(D-25 ↔ D-50)은 모양이 비슷하고 크기만 달라 **사진으로는 계열까지**, 기호는 하중·치수로 사람이 고른다.
  비스듬히 찍으면 형태가 찌그러진다 → '정면에서 찍기' 안내.
- **진행 관문**: 실물 사진 10~20장(사용자 제공)으로 top-5 정답률을 잰다. 80% 이상이면 화면에 붙이고, 아니면 계열 분류만 하거나 보류.
- **사전 시험 — 인터넷 사진으로 '윤곽·구멍 떼기' 만 (2026-11-11, 결과: 지금 방식으로는 안 됨)**
  - 사진: Wikimedia Commons·Openverse 의 열린 사용 허가 사진을 'lifting lug / padeye / lifting eye' 로 찾았다(27장 받음).
    실제로 판형 러그가 보이는 것은 6장뿐이었다 — 나머지는 갑판 매립형 padeye·sliding padeye 장비·글자판·사람. 정답 쪽이 없어 정답률은 못 잰다.
  - 방법: 밝기 Otsu 문턱 + 테두리 기준 극성 + 가장 큰 덩어리 + 안쪽 둥근 빈 곳 = 핀 구멍(numpy·scipy·Pillow).
    사진 전체 / 가운데 70% / 사람이 부재 하나 둘레를 고른 사각형(흉내) 세 경우.
  - 결과(눈 판정, 사각형 경우): 부재 윤곽과 구멍을 둘 다 바르게 뗀 사진 **0/5**(구멍 있는 것). 구멍만 맞음 1(파란 도장 링, 윤곽은 위 보와 붙음),
    윤곽만 맞음 1(구멍 없는 padeye). 실패 원인 = 철판 위 철판(같은 색), 녹·어두운 조명, 같은 부재가 쌓인 사진, 구멍 안으로 같은 색 배경이 보임, 극성 오판.
  - 판단: 조선소 사진은 러그가 블록과 같은 도장·같은 철판 위에 붙어 있어 이 시험 사진(03번, 실패)과 같은 조건일 가능성이 크다.
    문턱 기반 실루엣은 버리고, 하려면 ① 사용자가 러그 안·구멍 안을 한 번씩 찍는 씨앗 기반 영역 확장 ② 사진 대신 지금의 '러그 고르기 도우미'(계열·SWL) 강화 중 하나.
    시험 파일(세션 한정): 작업 임시 폴더 `seg/segment.py`·overlay 그림.
  - 도우미에 '구멍 지름·판 두께' 질문을 더하는 안도 따져 봤다(같은 날) — **효과 없음**. 러그 46쪽에서 계열 + SWL 이 이미 41묶음 중 40묶음을 1쪽으로 정한다.
    남는 1묶음은 SWL 이 없는 보강 BKT 6쪽인데 이름(RB·LDP·D-xxS)으로 갈린다. 구멍 지름은 샤클(= SWL)이 정해 SWL 과 겹친다.
    값 자체도 다 못 읽는다 — 도면 쪽에는 글자 층이 없고(쪽 번호뿐), 선 글자 인식(사전 = 33쪽 글꼴)으로 'Ø' 지름은 46쪽 중 8쪽, 'STEEL PLATE(두께' 는 약 30쪽만 나왔다.
    실제로 막히는 곳은 '실물을 보고 계열을 아는 것' 이다 → **계열 단추에 대표 도면의 정면도 그림을 붙였다**(사용자 결정, 같은 날 구현·미커밋).
    대표 기호와 정면도 상자는 `utils/drawingBook.js` `LUG_FAMILIES[].figure`(쪽을 눈으로 보고 정함), 큰 그림을 SVG viewBox 로 잘라 보인다.
    정한 기호가 색인에 없으면 하중 가운데 쪽 전체 그림으로 대신한다(`familyFigure`). 서버 변경 없음 — 다음 exe 부터.
    → 3단계 '사진 인식' 은 하지 않는다. 사진 관문(실물 10~20장)도 필요 없어졌다.
- 설치 제약: 이 PC·서버에 OpenCV·딥러닝 모델·로컬 비전 모델이 없다 → numpy·scipy·Pillow 로 만든다(외부 AI 로 사진을 보내지 않음).
