## 1. 목표

사용자가 모은 실제 CSV 로 만든 BDF 가 **사용자의 다시 전처리 없이 바로 해석되는 FE 모델**이 되게 한다.
안 되는 경우(자료가 실제로 없는 경우)는 엔진이 조용히 메우지 않고 **무엇이 왜 안 됐고 어떤 가정을 넣었는지** 기록으로 남긴다.

판단 원칙 세 가지.
1. **자료로 풀 수 있는 것을 추측으로 풀지 않는다.** CSV 에 이미 있는데 안 쓰는 정보(`wvol` 경계 상자, `stru` 소속, `division`)를 먼저 쓰고, 없는 정보는 AM 쪽 내보내기에 칸을 더하는 것을 함께 추진한다.
2. **형상을 움직이지 않는다.** 사용자가 RBE 를 고른 이유가 형상 보존이다. 노드를 새로 옮기는 처리는 이번 계획에서 늘리지 않는다(지금 있는 1 mm 병합, 연장 규칙은 그대로).
3. **연결 수를 줄이는 것이 목표가 아니다.** 떨어진 그룹 수만 보면 반경을 키워 아무 데나 묶는 쪽이 이긴다. 그래서 '잘못 이은 것'을 막는 지표를 같이 본다(4절).

자유단, 그룹 연결, 루프 닫기 RBE(합계 약 4,500개)는 모두 500 mm 이하로 짧다. 500 mm 넘는 것은 U-bolt 80, 장비 53(1000 넘는 것 17), 배관 부품 12다.

## 3. 핵심 질문에 대한 답 (재검토)

### Q1. RBE 연결이 최선인가

**실제로 붙어 있는 편심 연결에는 RBE2 가 맞다.** 축선이 안 만나는 용접 연결을 강체 오프셋으로 보는 것은 표준이고, 형상을 안 움직인다는 사용자 원칙에도 맞다.
CBEAM 오프셋이나 짧은 강성 보는 쓰지 않는다(오프셋은 Studio, 편집 계약, 다른 도구까지 바꿔야 하고, 강성 보는 단면을 지어내야 한다).

**하지만 지금 떠 있는 그룹의 상당수는 RBE 로 풀 문제가 아니다.** 배관 그룹은 받칠 구조가 자료에 없는 것이라 가까운 아무 구조에 강체로 묶으면 없는 하중 경로를 만든다.
그래서 "RBE 냐 아니냐"가 아니라 **연결마다 근거 등급을 매기는 것**으로 바꾼다.

| 등급 | 뜻 | 처리 |
|---|---|---|
| A 근거 있음 | 두 부재의 부피(구조는 축선 둘레 단면 범위, 배관과 장비는 `wvol` 상자)가 닿거나 겹침. U-bolt, 밸브 같은 CSV 가 말한 연결 | RBE2, 표시 없음 |
| B 추정 | 부피는 안 닿지만 정책 한도 안 | 정책에 따라 RBE2 + '추정 연결' 표시, 또는 안 이음 |
| C 자료 없음 | 받칠 상대가 모델에 없음 | 잇지 않음. 정책 선택지(5절)로만 처리하고 반드시 보고 |

⚠ 구조 부재의 부피는 정확히 못 세운다 — AM 의 `poss`/`pose` 가 단면의 어느 기준선(중립축, 상면 등)인지 CSV 에 없다. 그래서 구조 쪽 A 등급은 "축선에서 단면 최대 치수 안" 같은 넉넉한 범위로만 판정하고, 정확한 판정은 AM 내보내기에 칸이 생긴 뒤로 미룬다(7절).

장비와 집중질량은 RBE2 대신 **RBE3 를 기본**으로 한다(질량만 나르고 강성을 왜곡하지 않음. 10-27 실측에서 RBE2 스파이더가 처짐을 약 41% 줄였다).
루프 닫기 RBE(같은 그룹 안에서 가까운 부재끼리 묶는 1,016개)는 연결을 위한 것이 아니라 강성을 더하는 추정이다 — A 등급일 때만 남기는 것을 4단계에서 시험한다.

### Q2. RBE 를 묶는 과정의 오류

- RBE 를 만드는 모든 경로가 **하나의 생성기**를 거치게 하고, 생성기가 불변식을 검사한다: 종속 중복(FATAL 5289), 종속 자유도에 SPC(2101), 순환, 독립 노드가 다른 RBE 의 종속인 사슬.
- 병합 규칙은 1벌로. 단 병합이 커다란 강체 덩어리를 만들지 않는지 **RBE 한 개의 최대 길이와 종속 수**를 지표로 본다.
- 모든 RBE 에 근거 필드를 붙인다: 만든 단계, 등급(A/B), 간극, 원인 CSV 줄. **기존 `remark` 문자열은 바꾸지 않는다**(Studio, MU, WorkBench 판정이 읽는다) — 필드를 더하기만 한다.
- 부분 자유도 U-bolt 는 `--ubolt-full-fix` 없이는 시험 14세트가 모두 FATAL 9050 이라는 기록이 있다(엔진 CLAUDE.md). 엔진 기본값을 123456 으로 맞추는 것을 정한다(D5).

### Q4. Studio 없이 엔진만 돌 때의 결정권

엔진이 혼자 정해야 하는 항목은 아래 다섯 개다. 정책 파일 하나(`--policy <json>` 또는 이름)로 받고, 정책 이름은 **둘만** 둔다.

| 결정 항목 | 선택지 | `standard`(기본) | `strict` |
|---|---|---|---|
| P1 추정 연결(B 등급) | 잇고 표시 / 안 이음, 한도 mm | 잇고 표시, 한도는 1단계 뒤 확정 | 안 이음 |
| P2 받칠 구조 없는 배관(C 등급) | 그대로 두고 보고 / 그 자리에 SPC / 배관 그룹을 빼고 질량만 가까운 구조에 분배 | **그대로 두고 보고** | 같음 |
| P3 장비 질량 부착 | interPos 만 / 경계 상자 받침에 RBE3 | 경계 상자 RBE3 | interPos 만 |
| P4 아주 작은 떠 있는 그룹(요소 3개 이하 등) | 남김 / 질량 보고 후 지움 | 남기고 표시 | 남김 |
| P5 U-bolt 자유도 | CSV 값 / 123456 | 123456 | 123456 |

P2 의 기본을 "그대로 두고 보고"로 둔 이유: 받칠 구조가 1 m 넘게 없는 배관을 자동으로 묶거나 땅에 고정하면 모델은 돌지만 틀린 모델이 된다(권상 해석에서는 땅 고정이 하중을 받아 버린다). 이 항목은 용도(권상, 운송, 단독 해석)에 따라 답이 달라 엔진이 대신 정하면 안 된다. 사용자가 정책에서 고르면 그대로 따른다.

모든 자동 결정은 `00_Decisions.json` 에 남긴다(항목, 택한 처리, 등급, 거리, 대상 노드와 요소, CSV 줄). WorkBench 판정과 Studio 가 이 파일 하나를 읽는다.
종료 코드는 **바꾸지 않는다**(1판의 새 코드 3 은 뺀다 — 옛 백엔드가 실패로 읽는다). 완성 여부는 `00_Verdict.json` 으로 낸다.

## 4. 완성 기준과 지표

### 완성 기준 (`00_Verdict.json`)

| 기준 | 방법 |
|---|---|
| 모든 CSV 행이 변환, 병합, 제외(사유)로 설명됨 | 입력 감사 |
| 질량 대조: CSV 합계 대비 모델 차이 1% 이하(사유 있는 제외 뺌) | 엔진 |
| 연결 그룹 1개(또는 정책이 남긴 그룹이 모두 결정 기록에 있음) | 엔진 그래프 |
| RBE 불변식 위반 0 | 엔진 |
| 기구 없음: 그룹이 1개일 때 **자유-자유 고유치 해석에서 0 Hz 모드가 정확히 6개** | Nastran SOL 103, 회귀 장치에서만 |
| 실제 받침(다리 SPC)만으로 자중 해석 FATAL 0, AUTOSPC 0, 반력 = 자중 | Nastran SOL 101, 그룹별 SPC 덧붙이기 없이 |

자유-자유 기준은 실제로 시험했다(MSC 2013, `freefree_trial/`): 그룹 1개 모델(s002) = 0 Hz 모드 6개, 그룹 2개(s001) = 12개.
단 그룹이 많으면 해석 자체가 실패한다(26개 그룹 s004 = FATAL 7340, 3005). 그래서 **그래프로 그룹 수를 먼저 보고, 1개일 때만** 돌린다.
덤으로 첫 탄성 모드 주파수가 헐거운 부분을 알려 준다(s001 0.196 Hz ↔ s002 2.53 Hz) — 판정에는 안 쓰고 보고만 한다.

### 회귀 지표 (단계마다 이전 결과와 비교)

좋아져야 하는 것: 그룹 2개 이상 묶음 수, 떠 있는 그룹 수(원인 분류별), 질량 누락 행과 kg, FATAL, AUTOSPC, 완성 기준 통과 묶음 수.

**나빠지면 안 되는 것(과연결 방지)**:
- B 등급(추정) 연결 수와 가장 긴 것, U-bolt 가 아닌 배관–구조 RBE 수, RBE 한 개의 최대 길이와 종속 수, RBE 에 걸린 노드 비율.
- 결과가 바뀐 묶음마다 **새로 생긴 연결 목록**(노드 좌표, 간극, 등급)을 뽑아, 단계 끝에 사용자가 10개쯤 Studio 에서 눈으로 본다. 통과 숫자만으로 단계를 끝내지 않는다.

#### 검토 흐름과 검증 표시 (2026-11-12 사용자 지시, 설계안 — 미착수)

목표: 엔진이 사용자 대신 정한 것을 사용자가 승인해야 모델이 '검증 완료'가 된다. Studio 를 거치든 엔진만 쓰든, **BDF 만 보고도 검증 상태를 안다.**

1. **엔진(가장 먼저, 작음)**
   - `00_Decisions.json` 항목마다 `review`: `required`(사람이 봐야 함) | `info`(기록만). required 초안 = 추정 연결 중 등급 B, C(4a 등급), 받칠 구조 없는 U-bolt, 장비 질량 빠짐과 옮김, 떠 있는 그룹, 질량 판정 미달. 자동 RBE 의 collapsed, removed 와 등급 A 연결은 info.
   - 최종 BDF 머리에 주석 한 줄(호선 주석 `$ HiTessModelBuilder: HullNo=` 과 같은 방식이라 BDF 를 따로 옮겨도 따라간다):
     `$ HiTessModelBuilder: Review=REQUIRED Items=<필수 수>`, 필수가 0 이면 `Review=NONE`.
   - BDF 옆에 `<설계명>.review.json`(필수 항목 목록, 상태 required, 결정 파일 sha) — 사용자가 말한 '검증 필요 표시 파일'. 결과 폴더 전체 없이 BDF 만 받을 때 함께 준다.
2. **Studio(MB)**
   - 열자마자 필수 항목이 있으면 '검토' 창: 한 번에 하나, 3D 가 그 자리로 가고 엔진이 한 일과 이유 한 줄, [승인] [거절] [나중에].
     거절 = 그 결정을 되돌리는 편집 intent(자동 RBE → `deleteRigid`, 옮긴 질량점 → `moveMass`류 필요 여부 조사). 되돌릴 intent 가 없는 항목(받칠 구조 없는 U-bolt 등)의 거절 = '수동 수정 필요'로 표시만 남기고 사용자가 편집 도구로 고친다.
   - **같은 종류가 많으면 묶는다** — 3454 만 해도 남은 자동 RBE 가 440개라 하나씩은 불가능하다. [이 종류 N건 모두 승인] + 간극 큰 순 몇 개 보기. 그래서 필수 수를 줄이는 4a 등급이 먼저다.
   - 모두 결정하면 기존 편집 적용(`apply-edit-intent`)으로 편집 BDF 를 만들고 머리를 `Review=DONE Items=<n>`(누가, 언제, 무엇을 승인했는지는 `00_Review.json` 에) 로. '수동 수정 필요'가 남으면 `Review=MANUAL Items=<k>`.
     결정 내역은 결과 폴더 `00_ReviewResult.json`(phase 정규식에 걸려 백엔드, Studio 가 최종 산출물로 오인하지 않음 — 3단계에서 확인한 규칙).
3. **엔진만 쓴 경우(Studio 를 안 연 BDF)**
   - BDF 머리가 `Review=REQUIRED` 로 남는다. WorkBench MB 화면은 판정에 '검증 필요 N건'과 [Studio 에서 검토] 를 보이고, BDF 받기는 막지 않되 경고.
   - BDF 를 입력으로 받는 곳(GMU 권상 검증, Side Passage, 해상 운송, LogBook 보내기)은 머리 주석을 읽어 '검증 안 된 MB 모델' 경고(막지 않음). 읽는 코드는 호선 주석 읽기(`hull_no.resolve_bdf_hull_no`) 옆에.
   - 다시 열어 검토 = WorkBench '결과 다시 열기'로 그 결과 폴더를 Studio 로. ⚠ 작업 폴더는 30일 뒤 지워진다 — 그 뒤에는 보관 CSV 로 다시 만들어야 한다.
4. **결정(2026-11-12, 사용자)**: 검증 전 BDF 받기는 허용(경고만), 받는 곳도 경고만 하고 막지 않는다 — 검토를 강제하면 Studio 를 못 쓰는 경우(AM 단독 등)에 일이 멈춘다.
**엔진 표시 진행 기록 (2026-11-12, 엔진 미커밋, 회귀 `s6_review` Nastran 없이 — BDF 는 `s4a_grade3` 과 '$' 주석 말고 62/62 같음)**
- 파일 이름을 `<설계명>.review.json` 이 아니라 **`00_Review.json`** 으로 바꿨다 — 백엔드 `_pick_final_artifact` 는 phase 규칙에 안 맞는 가장 새 `.json` 을 최종 산출물로 고르므로, 그 이름이면 최종 모델 JSON 자리를 빼앗는다. phase 규칙 이름은 백엔드와 Studio 가 건너뛴다.
- `00_Decisions.json` 항목마다 `review`(required | info). required = 남은 B 연결, 그룹 통째 이동, 질량점 옮김과 부착 실패, 빠진 장비 질량, 받칠 구조 없는 U-bolt, 주 구조 밖 그룹.
- `00_Review.json` = status(required | none), run(결과 폴더 이름), units(검토 단위: B 는 떨어진 조립품마다, 나머지는 결정마다, 각 단위 state = pending). Studio 가 approved | rejected | manual 로 바꾸고 status 를 done | manual 로.
- 최종 BDF 머리(호선 주석 바로 뒤) `$ HiTessModelBuilder: Review=REQUIRED Items=<단위 수>`, 없으면 `Review=NONE` (`Cmb.Io.Nastran.BdfReviewMarker`). 결정 기록이 BDF 보다 뒤에 만들어져 다 쓴 BDF 를 다시 열어 넣는다 — 임시 파일에 쓴 뒤 바꿔 넣어 실패해도 원본이 잘리지 않는다.
  **실행 시각(Run)은 BDF 에 넣지 않는다**(리뷰 반영) — 같은 입력이면 BDF 가 바이트까지 같아야 회귀 비교와 LogBook '같은 BDF 막기'가 된다(두 번 빌드 바이트 동일 확인). 어느 실행의 검토인지는 `00_Review.json` run.
  리뷰 참고: 권상 Wire 포함 BDF(bridge `build_lifting_bdf`)는 JSON 으로 새로 써서 표시가 빠진다 — '받는 곳 경고' 단계에서 GMU 쪽은 입력 BDF 기준으로 본다.
- 편집 적용(`apply-edit-intent`)은 기준 BDF 의 표시 줄을 그대로 이어받는다 — 편집만으로 '검증 필요'가 사라지지 않게.
- 62묶음: 검증 필요 합 2,661(모델당 중앙 16, 없음 3, 큰 것 3476-4b652283 512). 종류: 떨어진 그룹 651, 질량점 옮김 539, 받칠 구조 없는 U-bolt 408, 그룹 이동 386, 빠진 장비 질량 192, 추정 연결 449(조립품 묶음 432 + 이름 없음 17), 부착 실패 36.
  → **Studio 검토 창은 '종류별 모두 승인'이 꼭 있어야 한다**(한 모델 수백 건). 질량점 옮김, 떨어진 그룹은 종류 묶음 단위를 엔진에서 더 줄일지 Studio 단계에서 다시 본다.
5. 한계: 주석은 글자라 손으로 고칠 수 있다(보안 장치가 아니라 작업 흐름 표시). 어느 실행의 검토인지는 결과 폴더의 `00_Review.json` run 으로 묶는다.
6. 순서: 4a(추정 연결 등급) → 엔진 표시(1) → WorkBench 판정과 받는 곳 경고(3) → Studio 검토 창(2). MB Studio 를 고치면 짝 Studio 싱크 대장에 적는다(MU 는 BDF 입력이라 '받는 곳 경고' 쪽).

## 8. 작업 규칙 (실행 세션용)

1. **한 번에 한 단계, 한 변경.** 변경마다 회귀를 돌리고 "바뀐 묶음, 이유, 새 연결 목록"을 남긴다. 숫자가 좋아져도 이유를 설명 못 하면 넣지 않는다.

3. 깨면 안 되는 약속: RBE `remark` 문자열, 최종 JSON 의 기존 필드 이름, phase 파일 이름 규칙(`^\d{2}_[A-Za-z]+\.(json|bdf)$` — 새 파일 `00_Decisions.json`, `00_Verdict.json` 도 이 모양이라 백엔드와 Studio 가 `00_` 파일을 phase 로 잘못 읽지 않는지 3단계에서 먼저 확인), 종료 코드 0, 1, 2 의 뜻, stdout 첫 줄 `출력 폴더:`. 필드는 더하기만 한다.

5. 엔진 저장소는 Public 이다 — CSV, 호선 자료, 이 계획서를 엔진 저장소에 넣지 않는다.
6. Nastran 은 영문 경로에서, 동시에 3개까지(모델당 메모리 추정 8 GB).
7. 70 InHouse exe 교체는 단계가 끝날 때만, 백업 접미사(`.bak_<날짜>_before_<내용>`)를 남긴다. 145 반영은 사용자 몫이고 보고에 '수동 교체 파일'을 적는다.
