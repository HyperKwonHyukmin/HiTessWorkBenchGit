Overview

이 페이지는 개별 솔루션의 상세 계산 로직이 아니라 WorkBench 앱 자체의 골격, 공통 역할, 코드 진입점을 추적하기 위한 문서입니다.

Shell Electron
Client React SPA
Server FastAPI
1
Electron Shell 개발 모드에서는 http://localhost:5173, 배포 모드에서는 frontend/dist/index.html을 로드합니다.
2
React SPA App.jsx가 Splash, Login, Main 상태를 관리하고 NavigationContext의 currentMenu 값으로 화면을 선택합니다.
3
API Layer 프론트엔드 src/api/*.js와 각 페이지가 FastAPI 서버의 /api/* 엔드포인트를 호출합니다.
4
FastAPI Backend app/main.py가 라우터를 등록하고, 각 라우터가 서비스 함수와 DB 세션을 사용합니다.
5
DB / File System MySQL은 사용자, 세션, 해석 이력, 공지/가이드/요청 기록을 저장하고, 해석 입출력 파일은 userConnection/ 아래에 저장됩니다.

문서 범위

구분 이 페이지에 기록 개별 페이지로 분리
공통 구조 Electron, React SPA, FastAPI, DB 연결 방식 해당 없음
화면 흐름 메뉴 선택, Context, 공통 레이아웃, 페이지 선택 방식 개별 솔루션 화면의 입력 폼, 결과 뷰어, 특수 상태
처리 흐름 API 호출, 작업 제출, 상태 조회, 다운로드의 공통 패턴 각 솔루션의 계산식, 외부 실행 파일, 결과 파일 구조
데이터 흐름 공통 테이블과 JSON 컬럼의 역할 솔루션별 input_info, result_info 세부 스키마

FrontEnd

프론트엔드는 React + Vite 기반이며 React Router 대신 자체 NavigationContext를 사용합니다.

진입 흐름

1
frontend/src/main.jsx React 앱의 최초 mount 지점입니다. 이후 App.jsx로 앱 제어가 넘어갑니다.
2
frontend/src/App.jsx 앱 상태를 splash, login, main으로 나누고, 버전 체크와 세션 체크 후 실제 WorkBench 레이아웃을 표시합니다.
3
frontend/src/components/layout/Layout 좌측 메뉴, 상단/본문 프레임, 공통 레이아웃을 담당합니다. 메뉴 클릭은 최종적으로 setCurrentMenu()로 이어집니다.
4
App.jsx:renderPage() currentMenu 문자열을 기준으로 Dashboard, Studio 진입 페이지, 관리자/지원 페이지, 개별 솔루션 페이지를 선택합니다.

상태와 Context

파일 역할 코드 파악 포인트
contexts/NavigationContext.jsx 페이지 히스토리와 현재 메뉴 관리 history currentIndex NAVIGATE
contexts/DashboardContext.jsx 해석 앱 메타데이터, 즐겨찾기, 글로벌 작업 상태 ANALYSIS_DATA, APP_REGISTRY_OVERRIDES, 앱 제목과 실제 menuName/API 매핑
contexts/AuthContext.jsx 사용자 세션 상태와 로그아웃 처리 localStorage의 사용자/토큰 정리, 인증 상태 전파
contexts/ToastContext.jsx 전역 토스트 알림 API 성공/실패, 작업 완료/오류 알림 표시 경로

프론트엔드 역할 지도

영역 주요 파일 역할 상세 분리 기준
앱 생명주기 App.jsx Splash, Login, Main 상태 전환과 세션 만료, 버전 체크, 관리자 메뉴 보호를 담당합니다. 공통 유지. 특정 페이지 동작은 솔루션 문서로 분리합니다.
메뉴/라우팅 NavigationContext.jsx, Layout.jsx, Sidebar.jsx React Router 없이 메뉴 문자열과 히스토리 스택으로 화면 이동을 제어합니다. 새 메뉴 추가 시 Workbench에는 연결 위치만 기록합니다.
앱 카탈로그 DashboardContext.jsx 솔루션 목록, 상태, 즐겨찾기, 글로벌 작업 상태의 기준 데이터를 제공합니다. 개별 솔루션의 업무 의미와 계산 흐름은 별도 페이지에서 기록합니다.
인증/세션 AuthContext.jsx, LoginScreen.jsx 사번 기반 로그인 결과를 localStorage와 Context에 저장하고 앱 전체에 전달합니다. 공통 유지. 관리자 페이지 권한 예외만 Admin 문서에서 확장합니다.
서버 통신 config.js, src/api/*.js API base URL, 서버 주소 변경, 기능별 REST 호출을 담당합니다. 솔루션별 request/response는 개별 페이지에 정리합니다.

메뉴와 화면 매핑

  • 앱 카탈로그 정보는 DashboardContext.jsx의 RAW_ANALYSIS_DATA와 APP_REGISTRY_OVERRIDES에서 시작됩니다.
  • 사용자가 메뉴를 누르면 setCurrentMenu(menuName)이 호출되고 NavigationContext가 현재 메뉴를 갱신합니다.
  • App.jsx:renderPage()가 currentMenu를 읽어 실제 페이지 컴포넌트를 반환합니다.
  • 개별 솔루션 상세 흐름은 여기서 다루지 않고, 이후 솔루션별 HTML 메뉴에서 별도로 기록합니다.

API 설정

  • frontend/src/config.js의 DEFAULT_API_BASE_URL이 기본 서버 주소입니다.
  • 사용자가 앱 안에서 서버 주소를 바꾸면 localStorage의 server_url 값이 우선 사용됩니다.
  • API 호출 파일은 frontend/src/api/ 아래에 기능별로 분리되어 있습니다.

프론트엔드 수정 시 우선 확인

  • 메뉴명이 DashboardContext.jsx와 App.jsx:renderPage()에 모두 맞는가?
  • 새 API 호출이 config.js의 base URL 정책을 따르는가?
  • 페이지 이탈 후 유지되어야 하는 상태가 Context 또는 상위 state에 있는가?
  • 관리자 전용 메뉴라면 ADMIN_MENUS와 권한 체크 흐름에 포함되어 있는가?

BackEnd

백엔드는 FastAPI 기반입니다. 공통 흐름은 main.py에서 앱과 라우터를 구성하고, 각 라우터가 서비스 함수 및 DB 세션을 호출하는 구조입니다.

서버 시작 흐름

1
app/main.py FastAPI 앱을 생성하고 CORS, 라우터, 정적 파일 경로를 등록합니다.
2
DB 초기화 models.Base.metadata.create_all(bind=database.engine)로 모델 기반 테이블 생성을 시도하고 run_schema_bootstrap()을 실행합니다.
3
lifespan 서버 시작 시 진행 중이던 작업을 Interrupted로 변경하고, 기본 가이드를 seed하며, userConnection/ 정리 스케줄러를 시작합니다.
4
Router Include 인증, 사용자, 해석, 시스템, 지원, 활동 로그, 계산기/솔루션 라우터를 app.include_router(...)로 등록합니다.

주요 라우터

라우터 역할 확인할 흐름
routers/auth.py 로그인, 회원가입, 사용자 확인 /api, /member, 세션 토큰 발급/검증
routers/analysis.py 해석 요청, 상태 조회, 이력, 다운로드 업로드 저장, 작업 제출, job_id 조회, 결과 다운로드 권한 검사
routers/users.py 사용자 승인 및 관리 관리자 권한, 사용자 활성/비활성 상태
routers/support.py 공지사항, 사용자 가이드, 기능 요청 지원 페이지의 CRUD와 DB 모델 연결
routers/system.py 서버/DB/큐 상태 확인 관리자 System Settings 화면과 연결
routers/activity.py 활동 로그와 사용 기록 버전 업데이트, 페이지 조회, 다운로드, 사용 리포트의 근거 데이터
routers/viewers.py, routers/newsletters.py 보조 기능 라우터 공통 앱 외의 뷰어/알림성 기능 연결 지점

백엔드 역할 지도

영역 주요 파일 역할 상세 분리 기준
앱 구성 main.py FastAPI 앱 생성, CORS, 라우터 등록, 시작 시 복구/seed/cleanup을 담당합니다. 공통 유지. 신규 라우터 추가 여부만 여기에 기록합니다.
요청 접수 routers/analysis.py, routers/_intake.py 업로드 파일 저장, 작업 폴더 생성, 작업 제출, 기본 DB 레코드 생성을 담당합니다. 솔루션별 입력 검증과 request payload는 개별 문서로 분리합니다.
권한/보안 dependencies.py, routers/_access_control.py 인증 토큰 검증, 소유자 확인, 작업/파일 접근 권한을 검사합니다. 공통 유지. 예외 정책이 생기면 해당 기능 문서에 사유를 기록합니다.
작업 상태 services/job_manager.py ThreadPoolExecutor, 인메모리 job 상태, DB write-through를 관리합니다. 개별 task 함수 내부 단계는 솔루션 문서에서 설명합니다.
계산 서비스 services/*_service.py 외부 실행 파일 호출, 계산 함수, 결과 파일 수집 등 실제 처리 로직을 담습니다. 이 페이지에서는 공통 역할만 설명하고, 세부 로직은 솔루션별 페이지로 분리합니다.

해석 작업 공통 흐름

  1. 프론트엔드가 파일 또는 입력값을 /api/analysis/.../request 계열 엔드포인트로 전송합니다.
  2. routers/analysis.py가 인증 사용자와 form의 employee_id 일치 여부를 확인합니다.
  3. routers/_intake.py의 helper가 작업 폴더를 만들고 업로드 파일을 저장합니다.
  4. services/job_manager.py와 서비스 함수가 실제 계산 또는 외부 실행 파일 호출을 담당합니다.
  5. 진행률은 메모리 상태와 DB의 Analysis 레코드에 반영됩니다.
  6. 완료 후 결과 경로와 메타데이터가 result_info에 저장되고, 다운로드는 /api/download 경로를 통해 이뤄집니다.

작업 진행 상태 일부는 메모리 기반입니다. 서버 재시작 시 진행 중이던 작업은 시작 시점에 Interrupted / Failed로 정리되는 흐름이 있습니다.

백엔드 수정 시 우선 확인

  • 새 라우터를 만들면 app/main.py에 include 되었는가?
  • 사용자 입력의 employee_id가 인증 토큰 사용자와 대조되는가?
  • 다운로드/파일 접근이 userConnection/ 하위로 제한되는가?
  • 긴 작업은 동기 응답이 아니라 job 기반 상태 조회 흐름을 따르는가?

DB

DB는 MySQL이며 SQLAlchemy 모델을 통해 접근합니다. 연결 설정과 세션 생성은 app/database.py, 테이블 정의는 app/models.py에 있습니다.

연결 흐름

1
app/database.py .env 값을 읽어 mysql+pymysql://... 형식의 DB URL을 구성합니다.
2
engine pool_recycle=3600, pool_pre_ping=True로 MySQL 연결 안정성을 보강합니다.
3
SessionLocal 요청별 DB 세션을 만들고 get_db() dependency가 요청 종료 시 close합니다.
4
models.Base 모든 SQLAlchemy 모델의 기반이며 main.py에서 테이블 자동 생성을 호출합니다.

주요 테이블

모델 테이블 역할 주요 컬럼
User users 사용자 계정과 권한 employee_id, is_active, is_admin, is_developer
UserSession user_sessions 서버측 세션 토큰 token, employee_id, expires_at
Analysis analysis 해석 작업 이력과 상태 job_id, program_name, job_status, progress, input_info, result_info
Notice notices 공지사항 type, title, is_pinned, author_id
UserGuide user_guides 사용자 가이드 category, title, content
FeatureRequest feature_requests 기능 요청 status, upvotes, admin_comment
ActivityLog activity_logs 로그인, 페이지 조회, 다운로드 등 활동 기록 employee_id, action_type, action_detail, status

DB와 화면 연결

  • 로그인/회원가입 화면은 User, UserSession 흐름과 연결됩니다.
  • My Projects, Analysis Management, Dashboard 통계는 주로 Analysis 테이블을 조회합니다.
  • Notice, User Guide, Feature Requests 페이지는 각각 Notice, UserGuide, FeatureRequest를 사용합니다.
  • Usage Reports 및 활동 추적은 ActivityLog에 의존합니다.

DB 역할 지도

흐름 읽기/쓰기 대상 관리 포인트
로그인/세션 User, UserSession, ActivityLog 사용자 활성 상태, 관리자 권한, 세션 만료, 로그인 이력을 함께 확인합니다.
해석 실행 Analysis 공통 상태 컬럼은 Workbench에서 관리하고, JSON 내부 구조는 솔루션별 문서에 둡니다.
지원/운영 Notice, UserGuide, FeatureRequest 지원 페이지 CRUD와 관리자 권한 체크가 함께 움직입니다.
사용량 리포트 Analysis, ActivityLog, User 통계 기준 변경 시 화면, API, XLSX export 결과를 같이 확인합니다.

DB 수정 시 우선 확인

  • 모델 컬럼 추가 후 기존 DB 스키마 보정 로직이 필요한가?
  • JSON 컬럼 구조 변경 시 프론트엔드 파싱 코드가 같이 바뀌는가?
  • 관리자 통계에서 개발자 또는 샘플 실행 데이터 제외 정책이 유지되는가?
  • 세션/인증 관련 변경은 AuthContext, auth.py, dependencies.py를 함께 확인했는가?

관리 포인트

이 HTML 문서는 코드 변경 시 같이 갱신하기 위한 체크리스트 역할을 합니다.

문서 갱신 기준

  • 새 Studio 또는 솔루션 메뉴가 추가되면 WorkBench 문서에는 공통 연결 위치와 역할만 기록하고, 상세 흐름은 별도 HTML로 분리합니다.
  • 공통 Context, 인증, API base URL, 작업 상태 관리 방식이 바뀌면 이 페이지의 FrontEnd/BackEnd/DB 섹션을 갱신합니다.
  • DB 모델 또는 JSON 컬럼 구조가 바뀌면 DB 섹션에 영향 범위를 기록합니다.
  • 해석 작업 공통 처리 방식이 바뀌면 BackEnd의 작업 공통 흐름을 먼저 수정합니다.
